feat(sharing): share boards with editors and viewers via invitations

Database (migration 000005)
- board_members (editor/viewer) + board_invites; the owner stays boards.created_by.
- Invites are pending until the invitee accepts with a CONFIRMED email, so the
  inviter cannot learn whether an address has an account (no enumeration) and an
  unconfirmed sign-up cannot claim invites. Capped at 50 pending per board.
- RLS rewritten per command: members read; owner and editors write; only the
  owner renames/deletes the board and manages members; members can leave.
  SECURITY DEFINER helpers (is_board_owner/member, can_edit_board) answer only
  about the current user. Memberships/invites are written only through RPCs.
- move_cards / move_columns now require edit permission instead of ownership.

Client
- Roles (owner/editor/viewer) on boards, ShareBoardDialog (invite, change role,
  remove, revoke, leave), received-invites panel, "shared" badge in the list.
- Viewers get a read-only UI (no drag, add, edit); RLS remains the authority.
- Boards/role refresh on realtime reconnect.

Tests
- tests/db: 25 tests on real Postgres (PGlite) covering isolation, roles,
  invites and RPC permissions; mutation-checked against 8 permission regressions.
- unit tests for role resolution and error mapping.

Deploy order: run migration 000005, then deploy the client (the new client
queries board_members, which does not exist before the migration).
